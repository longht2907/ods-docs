## Phạm vi L1

Áp dụng khi API trả HTTP error, timeout, response không đúng kỳ vọng hoặc chỉ lỗi trên một môi trường/endpoint.

## Triệu chứng

- HTTP 400/401/403/404/409/429, 5xx hoặc timeout.
- Response body có mã lỗi nhưng khách hàng chưa xác định nguyên nhân.
- Cùng request trước đây hoạt động nhưng hiện thất bại hoặc chỉ lỗi production.

### Phân nhánh nhanh

| Dấu hiệu | Nhận định ban đầu | Hành động tiếp theo |
| --- | --- | --- |
| `400` hoặc `422` | Request/payload không hợp lệ | Đối chiếu field, kiểu dữ liệu và encoding với API Reference |
| `401` hoặc `403` | Authentication, credential hoặc permission | Kiểm tra môi trường/quyền; không yêu cầu gửi token đầy đủ |
| `404` | Sai endpoint/resource hoặc resource không tồn tại | Đối chiếu base URL, path và ID tài nguyên |
| `409` | Xung đột trạng thái hoặc dữ liệu đã tồn tại | Không retry mù; kiểm tra trạng thái resource trước |
| `429` | Vượt rate limit | Tôn trọng `Retry-After`; giảm nhịp gọi thay vì tăng retry |
| `5xx` hoặc timeout | Lỗi dịch vụ/network; mutation có thể đã được xử lý | Lưu Request ID và kiểm tra kết quả trước khi retry |

## Cần hỏi khách hàng

- Endpoint, HTTP method, môi trường, thời điểm/múi giờ và Request/Correlation ID.
- Status code, response body và request body đã che credential/PII.
- Tần suất, phạm vi và thay đổi gần nhất ở code/config/network.
- Request là đọc dữ liệu hay mutation; đã retry bao nhiêu lần.

## Kiểm tra L1

1. Đối chiếu endpoint/method/header/content type và field bắt buộc với API Reference.
2. Kiểm tra credential có tồn tại/hết hạn/đúng môi trường nhưng không sao chép giá trị vào ticket.
3. Phân loại: 4xx thường thuộc request/auth/quyền; 429 thuộc giới hạn; 5xx/timeout cần phía dịch vụ.
4. So request lỗi với request thành công đã sanitize, gồm kiểu dữ liệu và encoding.
5. Kiểm tra DNS/TLS/network khi không nhận được HTTP response.

## Xử lý trong phạm vi L1

- Sửa endpoint/method/header/payload khi sai khác rõ với tài liệu đã công bố.
- Làm mới credential theo quy trình chính thức nếu hết hạn; không gửi token qua chat.
- Với 429, tuân thủ `Retry-After` nếu response có cung cấp; không tăng vòng lặp retry.
- Chỉ retry GET/read an toàn; mutation cần idempotency key hoặc xác nhận chưa tạo dữ liệu.

## Điểm dừng và chuyển cấp

- Request hợp lệ vẫn 5xx/timeout hoặc nhiều khách hàng cùng lỗi.
- Response contract khác tài liệu, dữ liệu đã được tạo nhưng client nhận timeout.
- Cần trace service/database, kiểm tra rate limit/quyền hoặc khôi phục dữ liệu.

## Dữ liệu chuyển cấp

- Endpoint/method/environment, timestamp, status, Request ID và latency.
- Sanitized headers/body/response; thay token bằng `[REDACTED]`.
- Số lần retry và bằng chứng kiểm tra dữ liệu đã/ chưa được tạo.

## Trả lời mẫu

> **Tiếp nhận:** ODS đã ghi nhận API trả lỗi. Vui lòng cung cấp endpoint, method, thời điểm, status code, Request ID và request/response đã che token cùng dữ liệu cá nhân.

> **Chuyển cấp:** Request đã được đối chiếu với tài liệu nhưng lỗi vẫn tái hiện. ODS đã chuyển đội API kiểm tra theo Request ID; tạm thời không retry mutation để tránh dữ liệu trùng.

## Nguyên nhân thường gặp và tra cứu

- Sai endpoint/method/header/payload, credential hết hạn hoặc thiếu quyền.
- Rate limit, network/TLS, service 5xx hoặc timeout sau khi backend đã xử lý.
